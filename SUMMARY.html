Reliable UDP Frame Streaming with XOR Forward Error Correction

Final architecture and design decisions for the Flaky Network assignment

1. Problem and objective

The harness produces one 160-byte frame every 20 ms. Frames cross an impaired UDP relay that may drop, delay, reorder, or duplicate packets. A frame is successful only when its correct sequence number and payload reach the player before its configured deadline.

The implementation must keep deadline misses at or below 1.00%, bandwidth overhead at or below 2.00x, and then minimize playout delay.

The sender and receiver communicate only through the relay path. The final design does not use the optional feedback channel.

3. Wire protocol

The sender-to-receiver protocol uses a packed packet structure:

FieldSizePurpose
Sequence number4 bytesIdentifies the original stream frame
FEC group2 bytesIdentifies the pair of frames protected together
Packet type1 byteDistinguishes DATA from PARITY
Payload160 bytesOriginal frame or XOR parity bytes

The sequence number and group identifier are converted to network byte order before transmission and converted back at the receiver.

4. Sender design

Each source frame is forwarded immediately as a DATA packet. Consecutive frames are grouped in pairs. For each pair, the sender computes:

parity[b] = first_payload[b] XOR second_payload[b]
for every payload byte b

After the second DATA packet of a group is sent, the sender sends one PARITY packet. Therefore, every two source frames produce three relay packets.

This choice intentionally spends additional bandwidth to reduce recovery delay. A 4+1 design waits three frame intervals before parity for the first frame can exist, whereas the 2+1 design waits only one 20 ms interval.

5. Receiver design

Packet validation

The receiver rejects packets with an unexpected size, out-of-range group or sequence number, or a DATA packet whose sequence number is inconsistent with its claimed FEC group.

Duplicate and reordering handling

Packets may arrive out of order. Group state independently records which DATA payloads and parity payload have arrived. An atomic flag associated with every output frame ensures that only the first valid original or recovered copy is forwarded.

Immediate forwarding

A valid DATA frame is sent directly to the player as soon as it reaches the receiver. The receiver does not wait until the nominal playback deadline because the harness accepts any correct arrival at or before that deadline. Immediate forwarding maximizes timing margin and avoids scheduler wake-up error.

FEC recovery

When parity and exactly one of the two DATA packets are present, the missing payload is reconstructed:

missing_payload = parity_payload XOR received_payload

The reconstructed frame is then forwarded through the same duplicate-safe output path.

6. Why retransmission was not used

A retransmission request would have to cross the hostile relay from receiver to sender, and the replacement frame would then have to cross it again. Both messages may be delayed or lost, making retransmission unsuitable for tight real-time deadlines. Forward error correction sends recovery information in advance and requires no round trip.

7. Bandwidth analysis

The packed protocol packet is 167 bytes: 7 bytes of metadata and 160 bytes of payload. The 2+1 design sends three packets per two raw frames. In the measured 1500-frame runs, it sent 2250 packets and 375750 bytes through the relay, corresponding to 1.57x overhead. This remains below the 2.00x limit.

The experiments identify the practical validity boundary for Profile B between 90 ms and 100 ms. Although the implementation remains valid at 100 ms, that operating point sits exactly on the permitted 1.00% miss-rate limit. The recommended grading delay is therefore 110 ms, which preserves the same measured 0.80% miss rate while reducing latency by 10 ms compared with the initial 120 ms operating point and providing additional safety margin on unseen network conditions.

9. Limitations

  • The XOR code can recover only one missing DATA packet per two-frame group.
  • If both DATA packets are lost, recovery is impossible.
  • If one DATA packet and the parity packet are both lost, recovery is impossible.
  • Packets that arrive after the harness deadline cannot be made useful.
  • The fixed 2+1 redundancy does not adapt to changing network conditions.

10. Final design summary

The final system uses a simple 2+1 XOR FEC protocol, immediate receiver forwarding, sequence-based validation, out-of-order storage, and atomic duplicate suppression. The final implementation achieves a measured bandwidth overhead of 1.57× while demonstrating valid operation at 60 ms on Profile A and 100 ms on Profile B, with 110 ms recommended as the grading delay for additional robustness on unseen network conditions.
